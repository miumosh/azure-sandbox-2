# テスト仕様書 作成指示書（別 AI 向け）

本書は、**この手順書一式からテスト仕様書を起こす作業を別の AI に依頼する**ための指示書。
以下の「依頼文」をそのまま渡し、必要なら「読ませる資料」に挙げたファイルを添付する。

本書自体は仕様書ではない。仕様書の**成果物イメージ・守らせるルール・検収チェックリスト**を定める。

---

## 0. この作業の位置づけ

- **既にあるもの**: 手順書（[01-storage-csv.md](./01-storage-csv.md) / [02-function-api.md](./02-function-api.md)）、
  テストデータ（`test/data/`）、期待値（各手順書の表と `test/data/api-requests/cases.json`）。
- **作らせたいもの**: それらを**1 件 1 行のテストケース一覧**に再構成した、実施・記録・報告に使える**テスト仕様書**。
- **やらせないこと**: 新しいテスト観点の発明、実装の変更提案、環境構築手順の記述。
  観点の追加が必要だと判断した場合は「追加提案」として**本文と分けて**列挙させる。

---

## 1. 依頼文（ここから下をコピーして渡す）

> あなたは Azure のデータ連携システムのテスト仕様書を作成するテクニカルライターです。
> 以下の資料を読み、**テスト仕様書 1 本**を Markdown で作成してください。
> 資料に書かれていない事実を推測で補ってはいけません。
>
> ### 対象システム
>
> 2 つの入口を持つ顧客情報連携システム。
>
> - **経路1（バッチ取り込み）**: CSV を Blob Storage の `input/` に置く → Event Grid の `BlobCreated` →
>   Azure Data Factory のパイプライン `pl_csv_ingest` → PostgreSQL。
>   検証 SQL が全行を判定し、合格行を `customer_info_production`、違反行を理由付きで `customer_info_error` に振り分ける。
> - **経路2（照合 API）**: `POST /api/customers/search`（Azure Functions）。
>   氏名カナ・生年月日・携帯番号の 3 項目完全一致で `policy_no` を返す。前段に AKS 上の中継アプリがある。
>
> ### 読ませる資料（すべて必読）
>
> | ファイル | 何が書いてあるか |
> | --- | --- |
> | `test/README.md` | 前提・実行環境・テストデータの命名規則（`valid` / `invalid_` / `scenario_` / `q(n)_`）・確認手段の制約 |
> | `test/01-storage-csv.md` | 経路1 の手順と全パターン（ファイル単位の期待値表 / 行レベル `OK-xx`・`V-xx` / ファイル投入レベル `L-xx`） |
> | `test/02-function-api.md` | 経路2 の手順と全パターン（`F-Axx` 成功 / `F-Bxx` NOT_FOUND / `F-Cxx` BAD_REQUEST / `F-Dxx` プラットフォーム層 / `F-Exx` サーバエラー / `K-xx` AKS 中継層固有） |
> | `test/data/api-requests/cases.json` | 経路2 の全ケースの入力と期待値（`expect` / `expect_via_aks`）。**経路2 の期待値はこれを一次情報とする** |
> | `test/data/csv/` | 経路1 のテストデータ本体。ファイル名と観点の対応は `test/README.md` を見る |
> | `docs/api-customer-search.md` | API 仕様（`result_code` の定義、エラーメッセージ、PII を出さない方針） |
> | `docs/pipeline.md` | パイプラインの構成と確認方法（`rowsRead` の読み方、トリガー条件） |
> | `docs/test.md` | 過去の実測結果（どこまで実機で確認済みか） |
>
> ### 実施環境の前提（仕様書にもこの前提で書くこと）
>
> - **CSV のアップロードは手動**。Storage Explorer / ポータル / CLI のどれを使うかは実施者に任せる。
>   仕様書には「どのファイルを・どのコンテナに・どの Blob 名で置くか」だけを書き、**アップロード操作の手順は書かない**。
>   規定の Blob 名は `input/ciupload39.csv`（同名上書き）。
> - **Function API のテストは、Function の Private Endpoint に NW 疎通できる VM から `curl` で実施する**。
>   リクエストは `test/data/api-requests/<ケース ID>.json` を**パス指定**で渡す（`curl -d @<file>`）。
>   **VM の作成手順やスクリプトは書かない**。VM が用意済みであることを前提条件として書く。
> - AKS 経由（経路2-B）は公開 LB なのでローカル端末から `curl` の form 送信で実施する。
> - 閉域のため、DB の中身は直接読めない。件数は ADF の `rowsRead`、理由の予測は
>   `test/scripts/csv/simulate_validation.py`、ライブ確証が要るときだけ踏み台 VM の `psql`。
>
> ### 成果物
>
> - ファイル: `test/test-spec.md`（Markdown 1 本）。
> - 構成:
>   1. **表紙情報** — 対象システム / 版数 / 作成日 / 前提環境 / 参照資料の一覧
>   2. **テスト方針** — 何を確かめるテストか、合否の考え方、実施順序の制約
>   3. **共通前提** — 実施前に整えておく状態（Terraform apply 済み、手動アップロード可能、疎通可能な VM、前提データ投入済み 等）
>   4. **テストケース一覧（本体）** — 下記の列で 1 ケース 1 行
>   5. **後片付け** — production を元に戻す手順
>   6. **付録** — テストデータ一覧（ファイル名 / 観点 / 行数 / 期待値）、用語集、未実測ケースの一覧
> - テストケース一覧の列（この順で固定）:
>
>   | 列 | 内容 |
>   | --- | --- |
>   | ID | 既存の ID を**そのまま流用**（`OK-xx` / `V-xx` / `L-xx` / `F-Axx`〜`F-Exx` / `K-xx`）。勝手に振り直さない |
>   | 大分類 | 経路1 / 経路2 |
>   | 中分類 | 正常系・必須違反・桁数違反・文字種違反・実在日違反・重複・ファイル投入・成功照合・該当なし・入力不備・プラットフォーム層・サーバエラー・AKS 中継層 |
>   | 観点 | 何を確かめるか（1 文） |
>   | 事前条件 | このケース固有の前提（例: 前提データ投入済み、前の run が Succeeded） |
>   | 入力データ | CSV ファイル名 / リクエスト JSON のファイル名。値そのものが要点の場合は値も書く |
>   | 実施手順 | 番号付きで簡潔に。経路1 は「規定名で手動アップロード → run 完了待ち」、経路2 は `curl` コマンド 1 行 |
>   | 期待結果 | pipeline の状態 / `rowsRead` の件数 / `error_message` / HTTP ステータス / `result_code` / `policy_no` |
>   | 確認方法 | 実際に叩くコマンド（`az datafactory ...` / `curl ...`）または参照先 |
>   | 判定基準 | OK と言える条件（期待結果と重複してよい。曖昧語は使わない） |
>   | 実施状況 | `実測済` / `未実測`（資料の記載に従う。**推測で「実測済」にしない**） |
>   | 実測結果 | 空欄（実施者が埋める） |
>   | 判定 | 空欄（実施者が埋める） |
>   | 備考 | 層による挙動差など、実施者が誤解しやすい点 |
>
> ### 守るルール
>
> 1. **期待値は資料からそのまま持ってくる。** 計算し直したり、丸めたり、言い換えたりしない。
>    経路2 は `cases.json` の `expect` / `expect_via_aks` を一次情報とし、`02-function-api.md` の表と食い違う場合は
>    **両方を併記して差異を指摘する**（勝手にどちらかを採用しない）。
> 2. **「未実測」を消さない。** 資料が「※未実測」「設計上の期待値」としているものは、仕様書でもその旨を残す。
> 3. **層による挙動差を潰さない。** 同じ入力でも SQL 側は error、Function 側は NOT_FOUND になるケースがある
>    （`01-storage-csv.md` の B-4 の注記、`02-function-api.md` の §4）。この差は仕様であり、備考に明記する。
> 4. **エラーメッセージは原文のまま**引用する（`policy_no too long (max 10)` など）。翻訳・整形しない。
> 5. **PII を書かない。** テストデータは全てダミーだが、API のエラーメッセージに入力値を含めない設計になっている点は
>    確認観点として残す。
> 6. **手順に環境構築を混ぜない。** VM 作成、Terraform apply、アップロード操作の詳細は対象外。
> 7. **1 ケース 1 観点。** 資料の表で 1 行になっているものを勝手にまとめたり分割したりしない。
>    ただしファイル単位の期待値表（`scenario_*.csv` ごとの production / error 件数）は、行レベルの `V-xx` とは
>    別のケース群として扱う（両方必要）。
> 8. **実行順序の制約を明記する。** パイプラインは直列実行が必須で、`customer_info_production` は毎回入れ替わる。
>    異常系を流した後は復旧が要る。経路2 は経路1 の前提データに依存する。
> 9. **表は Markdown の表**で書く。セル内改行が必要なら `<br>` を使う。
> 10. 出力は日本語。用語は資料の表記に合わせる（例: 「経路1 / 経路2」「production / error」「規定名」）。
>
> ### 迷ったときの扱い
>
> - 資料間で矛盾がある → **勝手に解決せず**、該当箇所に `⚠️ 要確認:` を付けて両論を残す。
> - 資料に期待値が無い観点 → ケースとしては起こしつつ、期待結果を `未定義（要確認）` とする。
> - 追加した方がよいと思った観点 → 本体に混ぜず、末尾に「追加提案」節を設けてそこに書く。

## 2. 検収チェックリスト（依頼元が確認する）

- [ ] ID が既存の体系（`OK-xx` / `V-xx` / `L-xx` / `F-Axx`〜`F-Exx` / `K-xx`）と 1 対 1 で対応し、**抜けが無い**
- [ ] 経路1 のファイル単位の期待値（`scenario_*.csv` ごとの production / error 件数）が資料と一致する
- [ ] 経路2 の期待値が `cases.json` の `expect` / `expect_via_aks` と一致する
- [ ] 「※未実測」が実測済みに化けていない
- [ ] アップロードは手動前提で書かれ、**アップロード操作の手順が書かれていない**
- [ ] Function のテストが **VM からの `curl` + リクエスト JSON のパス指定**で書かれている
- [ ] VM の作成手順・スクリプトが書かれていない
- [ ] 実行順序の制約（直列実行・production の入れ替わり・経路2 の依存）が書かれている
- [ ] 層による挙動差（SQL 側は error / Function 側は NOT_FOUND、AKS 経由は 422 or 200+BAD_REQUEST）が潰れていない
- [ ] エラーメッセージが原文のまま
- [ ] 実測結果・判定の記入欄が空で用意されている
