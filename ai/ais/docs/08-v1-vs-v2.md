# 「AI Foundry」とは何を指すのか — v1 (Hub) と v2 の違い

> 「Hub の v1」「Foundry v2」がそれぞれ何を指していて、Terraform でどうリソースが
> 違うのか分からない、という疑問への回答。

---

## 1. まず「AI Foundry」という語が 3 つの別物を指している

**これが混乱の根本原因。** 同じ「AI Foundry」でも文脈で実体が変わる。

| 呼び方 | 実体 | ARM リソースか |
|---|---|---|
| AI Foundry **ポータル** | `ai.azure.com` という **Web サイト** | ❌ ただの閲覧 UI |
| AI Foundry **Hub** | `Microsoft.MachineLearningServices/workspaces` (kind=Hub) | ✅ |
| AI Foundry **リソース / アカウント** | `Microsoft.CognitiveServices/accounts` (kind=AIServices) | ✅ |
| AI Foundry **プロジェクト** | **上記 2 つの下にそれぞれ別種類が存在する** | ✅ |

そして `ai.azure.com` は **v1 系と v2 系のプロジェクトを同じ一覧に並べて表示する**。
画面の見た目が同じでも裏にいるリソースは別物になり得る。

---

## 2. v1 と v2 の対比

| | **v1 (Hub ベース / classic)** | **v2 (アカウントベース / 現行)** |
|---|---|---|
| **親リソース** | `Microsoft.MachineLearningServices/workspaces` (kind=**Hub**) | `Microsoft.CognitiveServices/accounts` (kind=**AIServices**) |
| **プロジェクト** | `.../workspaces` (kind=**Project**) — 独立したリソース | `.../accounts/projects` — **アカウントの入れ子** |
| 実体 | Azure ML workspace の派生 | Cognitive Services アカウントの拡張 |
| **Storage Account** | **必須** | **不要** (Agent の Standard Setup を使う場合のみ必要) |
| **Key Vault** | **必須** | **不要** (同上) |
| Application Insights / ACR | 任意 | 任意 |
| **受信の閉域化** | Hub 自身の `publicNetworkAccess` + PE (subresource `amlworkspace`) | **親アカウント**の `publicNetworkAccess` + PE (subresource `account`) |
| **送信の閉域化** | `managedNetwork` (**Microsoft 管理サブスクに Hub 専用 VNet**) | `networkInjections` (**あなたの VNet のサブネットに注入**) |
| Private DNS Zone | `privatelink.api.azureml.ms`<br>`privatelink.notebooks.azure.net` | `privatelink.cognitiveservices.azure.com`<br>`privatelink.openai.azure.com`<br>`privatelink.services.ai.azure.com` |
| 推論エンドポイント | connection 経由で AI Services を参照 | **アカウント自身がエンドポイント** |
| 得意なこと | managed compute / prompt flow / 評価 | 推論 / Agent Service / Playground |
| ポータル URL の見分け | `.../Microsoft.MachineLearningServices/workspaces/...` | `.../Microsoft.CognitiveServices/accounts/...` |

### 決定的な違い

> **v1 の Hub は「AI を動かすワークスペース」で、AI Services とは別リソース。
> connection を張らないと繋がらない。**
>
> **v2 のアカウントは「AI Services そのもの」。プロジェクトはその入れ子なので、
> 最初から一体で接続は不要。** フォルダの権限がその中のファイルに効くのと同じ関係。

本構成の `ai/ai_foundry` (先行検証) では Hub と AI Services の connection が**空**で、
「v1 系と v2 系が独立した 2 系統」になっていた。これは珍しい事故ではなく、
素直に両方作ると起きる標準的な状態。

## 3. Terraform のリソース対応表

| 概念 | v1 (Hub) | v2 (アカウント) |
|---|---|---|
| 親 | `azurerm_ai_foundry` | `azurerm_cognitive_account` (`kind = "AIServices"`) |
| プロジェクト | `azurerm_ai_foundry_project` | `azurerm_cognitive_account_project` |
| モデルデプロイ | (Hub 経由では不可) | `azurerm_cognitive_deployment` |
| 必須の Storage | `azurerm_storage_account` (必須) | 不要 |
| 必須の Key Vault | `azurerm_key_vault` (必須) | 不要 |
| 受信 PE | `azurerm_private_endpoint` (`subresource_names = ["amlworkspace"]`) | `azurerm_private_endpoint` (`subresource_names = ["account"]`) |
| 送信 | `managed_network { isolation_mode }` ブロック | `network_injection { scenario, subnet_id }` ブロック |

### v1 のコード (本構成 `hub.tf`)

```hcl
resource "azurerm_ai_foundry" "this" {
  name                = "aif-aissbx"
  location            = azurerm_resource_group.this.location
  resource_group_name = azurerm_resource_group.this.name

  storage_account_id = azurerm_storage_account.hub[0].id   # ← 必須
  key_vault_id       = azurerm_key_vault.this[0].id        # ← 必須

  public_network_access = "Disabled"                       # ← 受信

  identity { type = "SystemAssigned" }

  managed_network {                                        # ← 送信
    isolation_mode = "AllowInternetOutbound"
  }
}

resource "azurerm_ai_foundry_project" "this" {
  name               = "aifp-aissbx"
  location           = azurerm_ai_foundry.this[0].location
  ai_services_hub_id = azurerm_ai_foundry.this[0].id       # ← 親を指す
  identity { type = "SystemAssigned" }
}

# 受信 PE
resource "azurerm_private_endpoint" "hub" {
  private_service_connection {
    private_connection_resource_id = azurerm_ai_foundry.this[0].id
    subresource_names              = ["amlworkspace"]      # ← v1 固有
  }
  private_dns_zone_group {
    private_dns_zone_ids = [
      azurerm_private_dns_zone.this["azureml"].id,           # api.azureml.ms
      azurerm_private_dns_zone.this["azureml_notebooks"].id, # notebooks.azure.net
    ]
  }
}
```

### v2 のコード (本構成 `main.tf` / `modules/cognitive_account`)

```hcl
resource "azurerm_cognitive_account" "this" {
  name                  = "ais-aissbx-xxxxx"
  kind                  = "AIServices"                     # ← これで v2 になる
  sku_name              = "S0"
  custom_subdomain_name = "ais-aissbx-xxxxx"               # ← PE には必須

  public_network_access_enabled = false                    # ← 受信
  project_management_enabled    = true                     # ← 入れ子プロジェクトを許可

  identity { type = "SystemAssigned" }

  network_injection {                                      # ← 送信
    scenario  = "agent"
    subnet_id = azurerm_subnet.this["agent"].id
  }
  # Storage も Key Vault も要らない
}

resource "azurerm_cognitive_account_project" "aiservices" {
  name                 = "proj-aissbx"
  location             = azurerm_resource_group.this.location
  cognitive_account_id = module.cognitive["aiservices"].id  # ← 親を指す
  identity { type = "SystemAssigned" }
}

# 受信 PE
resource "azurerm_private_endpoint" "this" {
  private_service_connection {
    private_connection_resource_id = azurerm_cognitive_account.this.id
    subresource_names              = ["account"]           # ← v2 は常にこれ 1 種類
  }
  private_dns_zone_group {
    private_dns_zone_ids = [ /* cognitiveservices / openai / services.ai */ ]
  }
}
```

**v2 のほうが圧倒的に短い。** Storage / Key Vault とその PE / DNS ゾーンが
まるごと不要になるため。

## 4. ★ 送信の閉域化 — v1 と v2 で方式が根本的に違う (実測)

ここが `managed_network` と `virtual network injection` の違い。

| | **v1: `managed_network`** | **v2: `network_injection`** |
|---|---|---|
| VNet はどこにあるか | **Microsoft 管理のサブスクリプション内** | **あなたの VNet** |
| あなたから見えるか | ❌ 中身は不可視 | ✅ サブネットとして見える・管理できる |
| 何が作られるか | Hub 専用 VNet + マネージド PE (outbound rules) | 委任サブネットに Container Apps 環境が注入される |
| 事前準備 | 不要 | **`Microsoft.App/environments` への委任サブネットが必要** |
| ARM プロパティ | `properties.managedNetwork.isolationMode` | `properties.networkInjections[]` |
| 後から追加 | ✅ 可能 | ❌ **作成時にしか設定できない。再作成が必要** |
| 作成時間 (実測) | Hub 1 分 15 秒 | アカウント **5 分 35 秒** |

### 4.1 実測 — v2 injection は自分の VNet に実体を作る

```bash
$ az rest ... /accounts/aisinj-aissbx-xxxxx --query "properties.networkInjections"
[
  {
    "scenario": "agent",
    "subnetArmId": ".../virtualNetworks/vnet-aissbx/subnets/snet-agent",
    "useMicrosoftManagedNetwork": false      # ← ★ここが v1 との分岐点そのもの
  }
]
```

**`useMicrosoftManagedNetwork: false`** — ARM のプロパティ名が、
そのまま「Microsoft 管理ネットワークを使わない = あなたの VNet を使う」と宣言している。

そして**あなたのサブネットに実体が作られる**:

```bash
$ az network vnet subnet show -g rg-aissbx --vnet-name vnet-aissbx -n snet-agent
{
  "prefix": "10.60.40.0/24",
  "delegations": [
    { "name": "Microsoft.App.environments",
      "svc": "Microsoft.App/environments",
      "state": "Succeeded" }
  ],
  "sal": [
    { "name": "legionservicelink",
      "linkedResourceType": "Microsoft.App/environments",   # ← Container Apps 環境
      "link": ".../subnets/snet-agent" }
  ]
}
```

**`serviceAssociationLinks` (SAL)** が張られている。
これは「このサブネットは Microsoft.App/environments に占有されている」という印で、
**これがある限りサブネットを消せない**（削除順序の罠、§6）。

### 4.2 実測 — v1 managed_network は自分の VNet に何も作らない

同じ VNet のサブネット一覧:

```
Name                Prefix         Delegation
------------------  -------------  --------------------------
AzureBastionSubnet  10.60.30.0/26
snet-pe             10.60.10.0/24
snet-jumpbox        10.60.20.0/24
snet-agent          10.60.40.0/24  Microsoft.App/environments   ← v2 injection だけ
```

**v1 の Hub は `managed_network` を有効にしても、あなたの VNet に何も作らない。**
作られるのは Microsoft 側で、あなたに見えるのは outbound rules の一覧だけ
([07-managed-network.md](07-managed-network.md))。

### 4.3 図で見る差

```
【v1: managed_network】
  あなたの VNet                    Microsoft 管理のサブスク
  ┌──────────────┐                ┌────────────────────────┐
  │ snet-pe      │                │  Hub 専用マネージド VNet │
  │  └ PE (受信) │◄───────────────│  ├ compute             │
  │              │   マネージド PE  │  ├ prompt flow         │
  └──────────────┘   (Azure が自動) │  └ 評価ジョブ           │
        ▲                          └────────────────────────┘
        │                                中身は不可視
   利用者/踏み台


【v2: network_injection】
  あなたの VNet
  ┌───────────────────────────────────────┐
  │ snet-pe          snet-agent            │
  │  └ PE (受信)      └ Container Apps 環境 │  ← ここに注入される
  │       ▲            (legionservicelink) │     自分で見える・管理できる
  │       │                 │              │
  └───────┼─────────────────┼──────────────┘
          │                 │
     利用者/踏み台      Storage / Cosmos / AI Search へ
                       (同じ VNet 内 or peering)
```

**v2 のほうが「自分の境界にトラフィックが留まる」**という点で強い。
その代わり、サブネット設計とライフサイクル管理の責任を自分が負う。

## 5. v2 injection の要件と制約 (MS Docs + 実測)

### 要件

| 項目 | 内容 |
|---|---|
| サブネット委任 | **`Microsoft.App/environments`** (必須) |
| サブネットサイズ | 最小 `/27`、**推奨 `/24`** (Container Apps の要件に由来) |
| アドレス空間 | RFC1918 (`10/8`, `172.16-31/12`, `192.168/16`) または CGNAT (`100.64/10` の一部)。**パブリック IP レンジ不可** |
| サブネットの共有 | ❌ **Foundry リソース 1 つにつき専用サブネット 1 つ**。共有不可 |
| リージョン | **Foundry リソースと VNet は同一リージョン**必須 |
| RP 登録 | `Microsoft.App` / `Microsoft.ContainerService` / `Microsoft.CognitiveServices` / `Microsoft.Network` など |

本構成の実装:

```hcl
# locals.tf
agent = {
  name             = "snet-agent"
  address_prefixes = ["10.60.40.0/24"]
  delegation = {
    name         = "Microsoft.App.environments"
    service_name = "Microsoft.App/environments"
    actions      = ["Microsoft.Network/virtualNetworks/subnets/join/action"]
  }
}
```

### 制約

| 制約 | 内容 |
|---|---|
| **後から追加できない** | 「network injection は**アカウント作成時に含める必要がある**。既存アカウントへの追加は非対応」。本構成が専用アカウント `aisinj-*` を別に立てているのはこのため |
| outbound 設定の変更不可 | 委任サブネットの変更もできない。**再デプロイが必要** |
| Agent Standard Setup | Agent Service をフルに使うには **BYO で Storage + Cosmos DB + AI Search の 3 つすべて**が必要。1 つでも欠けるとエラー |
| Code Interpreter | プライベート構成ではファイルのアップロード / ダウンロードを伴うシナリオが動かない |
| Blob + File Search | Azure Blob Storage のファイルを File Search で使うのは非対応 |
| 削除順序 | **Foundry リソースを purge してから VNet を消す**。逆順だと SAL が残って詰む (§6) |

> 出典: [Set up private networking for Foundry Agent Service](https://learn.microsoft.com/azure/ai-services/agents/how-to/virtual-networks)

### Agent Standard Setup で必要な追加の DNS ゾーン

本構成は injection の成立確認までで、Agent Service のフル構成は組んでいない。
フルに使う場合は以下が追加で要る:

| リソース | subresource | ゾーン |
|---|---|---|
| Azure AI Search | `searchService` | `privatelink.search.windows.net` |
| Azure Cosmos DB | `Sql` | `privatelink.documents.azure.com` |
| Azure Storage | `blob` | `privatelink.blob.core.windows.net` |

## 6. ★ 削除順序の罠

v2 injection を使うと、サブネットに **`legionservicelink`** という
serviceAssociationLink が張られる。これがあるとサブネットを削除できない。

MS Docs のトラブルシュートに載っているエラー:

```
Subnet requires any of the following delegation(s) [Microsoft.App/environments]
to reference service association link .../serviceAssociationLinks/legionservicelink.
```

**正しい順序:**

1. Foundry アカウントを削除する
2. **論理削除された Foundry アカウントを purge する**
3. そのあとに VNet / サブネットを削除する

```bash
# 2 の purge
az cognitiveservices account purge -g rg-aissbx -n aisinj-aissbx-xxxxx -l japaneast
```

本構成は `providers.tf` で `purge_soft_delete_on_destroy = true` を設定済みのため、
`terraform destroy` なら自動で purge される。

## 7. どちらを使うべきか

| 要件 | 選択 |
|---|---|
| 推論エンドポイントを使うだけ | **v2 のみ。** Hub も Storage も Key Vault も不要 |
| Agent Service を使う | **v2。** injection + BYO (Storage/Cosmos/AI Search) |
| Playground / Chat で試す | **v2。** アカウント + プロジェクトで完結 |
| **managed compute** (自前のコンピュートでジョブを流す) | **v1 が必要** |
| **prompt flow** | **v1 が必要** |
| **評価 (evaluation) の Hub ベース機能** | **v1 が必要** |
| 送信トラフィックを自分の VNet 境界に留めたい | **v2** (injection)。v1 は Microsoft 側の VNet になる |

> **迷ったら v2 から始める。** v1 が要るのは Hub ベースの機能を使うときだけで、
> それ以外では Storage / Key Vault / それらの PE と DNS ゾーンという
> 大きな依存を背負い込むだけになる。

先行検証 `ai/ai_foundry` は v1 と v2 を**両方作ったうえで繋いでいない**状態だった。
これは「両方作ると自然に起きる」状態なので、先に方針を決めること。

### CLI で棚卸しする

```bash
SUB=<subscription-id>; RG=rg-aissbx

# --- v1: Hub / Project と、その connection (空なら AI Services と未接続) ---

  -g $RG --query "[].{name:name, kind:kind}" -o table

az rest --method get \
  --url "https://management.azure.com/subscriptions/$SUB/resourceGroups/$RG/providers/Microsoft.MachineLearningServices/workspaces/aif-aissbx/connections?api-version=2024-10-01" \

az resource list --resource-type Microsoft.CognitiveServices/accounts \
  -g $RG --query "[].{name:name, kind:kind}" -o table

az rest --method get \
  --url "https://management.azure.com/subscriptions/$SUB/resourceGroups/$RG/providers/Microsoft.CognitiveServices/accounts/ais-aissbx-xxxxx/projects?api-version=2025-06-01" \
  --query "value[].{name:name, isDefault:properties.isDefault}" -o table

# --- 送信の方式を確認する ---
# v1: managedNetwork があるか
az rest --method get --url ".../workspaces/aif-aissbx?api-version=2024-10-01" \

# v2: networkInjections があるか (useMicrosoftManagedNetwork が false なら自分の VNet)
az rest --method get --url ".../accounts/aisinj-aissbx-xxxxx?api-version=2025-06-01" \

```

## 9. 実測まとめ

| 項目 | 結果 |
|---|---|
| `azurerm_cognitive_account` の `network_injection` ブロック | ✅ azurerm 4.76.0 に存在 (`scenario` / `subnet_id`) |
| `Microsoft.App/environments` 委任サブネットでの作成 | ✅ 成功 (`10.60.40.0/24`) |
| 作成時間 | **5 分 35 秒** (通常のアカウントは数秒) |
| ARM プロパティ | `networkInjections[].useMicrosoftManagedNetwork = false` |
| サブネットへの影響 | `serviceAssociationLinks: legionservicelink` (`Microsoft.App/environments`) |
| 受信 PE との併用 | ✅ 可能。`public_network_access_enabled = false` + PE と同時に成立 |
| サブネットの IP 消費 (作成直後) | **0 / 251**。Agent 実行時にオンデマンドで消費されると推測 **[未検証]** |
| v2 プロジェクトの自動生成 | ❌ されない (`projects` は空)。明示的に作る必要がある |
| Agent の実行 | **[未検証]**。BYO (Storage/Cosmos/AI Search) を組んでいないため |

> **injection の「成立」までは確認したが、Agent を実際に動かしてはいない。**
> フル検証には Cosmos DB / AI Search / Storage の BYO 一式が必要
> (MS Docs のサンプル `15-private-network-standard-agent-setup` 相当)。
